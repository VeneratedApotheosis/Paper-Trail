## 1. Concept & Visa fit
"Your inbox already knows what you're owed." Read-only Gmail → every purchase becomes a ledger row → agent flags **refunds owed**, **return deadlines**, **price-drop adjustments**, and **rewards left on the table**, and drafts (never sends) the follow-up. Persona: online shopper with 20+ orders/quarter who loses $100s to missed returns and silent refund failures.
Visa stages covered: **post-purchase** (core), **loyalty** (card/points ledger), **payments** (which card paid, last4), + optional **decision/checkout** (Card Advisor: paste merchant+total → best card, stretch). Honest weakness: no money movement → lean on Trust 15 + UX 25 + a measurable "$ recovered" number. Do not claim Visa API integration; cards are user-entered with last4/network label.

## 2. Architecture & stack
- **Web:** Next.js (App Router) + TS + Tailwind + Framer Motion; tokens exported from Paper. **API/worker:** same repo (Next route handlers + in-process job queue; BullMQ only if time). **DB:** SQLite (Drizzle) for dev/demo, Postgres (Neon) if hosted [A]. Deploy Vercel/Fly [A]; *demo can run localhost on 2 laptops* (OAuth redirect simpler).
- **Pipeline (typed stages, each writes an audit row):** `gmail.sync` → `prefilter` (Gmail query + sender/keyword heuristics) → `redact` (strip PANs, phones, street addrs, replace with tokens before any LLM call) → `classify` (cheap LLM or rules: order_confirm | shipped | delivered | return_started | return_received | refund | price_adjust | cancel | marketing | not_receipt) → `extract` (LLM structured output, zod/JSON-schema, per-field `confidence` 0-1 + `evidence` quote ≤200 chars) → `normalize+match` (group events into orders by order_id → else merchant+amount+date proximity) → `rules` (pure TS, deterministic, injectable clock) → `alerts/drafts` (LLM writes wording only; numbers come from rules).
- **LLM:** one primary (Claude/GPT [A], key needed) w/ JSON-schema output; cache by `sha256(redacted_text)` so reruns are free/offline; fixtures for demo mode. Optional StepFun only if truly load-bearing (default skip).
- **Gmail ingest [V]:** `messages.list` (q-filter) then `messages.get` format=full (**quota 60 units each**, list=5; limits 6,000 units/user/min, 1.2M/project/min) → ~100 msgs/min/user safe; first sync capped to last 90 days, ≤300 msgs, batched w/ backoff on 429. Incremental via `history.list` [A]; push/Pub/Sub watch = **cut** (use manual "Sync now" + 5-min poll). Skip PDF attachments (cut line).
- **Demo-mode** (no OAuth): same pipeline fed from `seed/inbox.json` — the guaranteed path for judges/Devpost link.

## 3. Data model (SQL-ish; all rows user-scoped; no raw bodies stored)
- `user(id, google_sub, token_enc, created_at)` · `card(id, label, network, last4, reward_rules_json)` (user-entered/presets, labeled "illustrative").
- `message(id, gmail_id UNIQUE, thread_id, received_at, from_domain, text_hash, class, class_conf, extract_json, evidence_snips, processed_at)` — raw body discarded after extraction; snippets ≤200 chars each.
- `merchant(id, name, domains[], category, return_window_days, window_anchor ENUM(order|delivery), refund_sla_days, price_adjust_days, policy_source ENUM(email_text|default_table|user), policy_quote)`.
- `order(id, merchant_id, order_ref, placed_at, currency, subtotal, tax, shipping, discount, total, card_id?, last4?, status, conf_min)`; `line_item(id, order_id, sku?, name, qty, unit_price, returned_qty)`.
- `event(id, order_id, type ENUM(shipped|delivered|return_started|return_dropped|return_received|refund_issued|store_credit|price_adjust|cancel), at, amount?, message_id, conf)`.
- `price_obs(id, line_item_id, price, source ENUM(mock|json_ld|api|email_promo|user), observed_at)`.
- `finding(id, order_id, kind ENUM(refund_overdue|refund_short|return_deadline|price_drop|rewards_gap), amount_at_stake, due_at, severity, status ENUM(open|drafted|resolved|dismissed), rule_version, explain_json)`; `draft(id, finding_id, subject, body, approved_at)` (copy-to-clipboard/mailto only).
- `audit(id, at, actor ENUM(user|system|llm), action, subject_id, meta_json)` — every Gmail fetch (count + query), LLM call (redacted-token count, model, cost), approval, delete.
- `gold_label(message_id, fields_json)` + `eval_run(id, at, model, metrics_json)` for the parsing eval.

## 4. Detection rules (exact; `rules.ts`, versioned, property/table-tested, clock injected as `now`)
**R1 Refund owed.** Trigger event T = earliest of `return_received` (strong) or `return_dropped|return_started with carrier scan/label` (weak). Expected-by `E = T + N`, N = `merchant.refund_sla_days` if stated in email text, else default **10 days after received / 14 after drop-off-only** (editable table [A: typical retailer SLAs vary 3-14d; label as defaults]). A refund is *matched* if an `event.refund_issued` exists with same `order_ref`, else same merchant + |amount − expected| ≤ max($0.50, 2%) and `at ≥ T`. Findings: `now>E` & no match → **refund_overdue** (severity by $); `now∈[E−3d,E]` → "due soon"; match with amount < expected − tolerance → **refund_short** (shows delta; tax/shipping-fee explainer); `store_credit` where original tender was card → flag "issued as credit, not refund". `refund initiated` email but N2=10 business days with no further info → "verify on statement" (we can't see the bank). Expected = Σ(returned_qty×unit_price)+prorated tax (− restocking fee if policy_quote says so).
**R2 Return deadline.** Anchor A = `delivered_at` if policy says "of delivery" (and a delivered event exists), else `placed_at` (or ship date if text says). `deadline = A + window_days`. Window precedence: (1) number parsed from email policy text via LLM (`policy_quote` kept as evidence) → (2) merchant default table → (3) unknown ⇒ show "policy unknown", no alert. Seasonal extensions ("through Jan 31") override if quote present. Non-returnable keywords (final sale, perishable, gift card, custom) ⇒ suppress. Alerts at T−7d, T−2d, expired; suppressed once any return event exists. Confidence <0.7 on window ⇒ badge "check policy" and link to quote.
**R3 Price drop.** For each open line item inside `price_adjust_days` (policy, else default 14, [A]): `drop = (paid − current) × qty`; fire if `drop ≥ max($5, 5% of paid)`, same SKU/variant, seller = merchant itself (not marketplace third party), not clearance/final-sale; value shown net of expected effort. Draft: policy quote + order ref + old/new price + evidence URL/time. Price sources (ladder, UI always labels source + observed_at):
  1. **Mock feed (default, ships h10):** `price_feed.json` with scripted drops + a "fast-forward N days" demo control. Labeled "simulated".
  2. **In-inbox signal:** promo/price-drop emails from the same merchant mentioning the SKU (extracted like any email) → `email_promo`. Real, zero new APIs, demo-able in seeded inbox.
  3. **Product-page JSON-LD** (`schema.org/Offer`) fetch for 1-2 friendly/own-hosted "mock store" pages we control; real retailers [A] block bots/ToS risk → don't scrape Amazon.
  4. **API** (DummyJSON [V per S9 dive, 5 laptops, toy], Best Buy dev key [A, instant?]) — only if time; stretch.
**R4 Rewards gap.** Merchant→category (LLM, cached) × user's `card.reward_rules` → `best_card` vs `used_card`; gap = (best_rate − used_rate) × total; monthly sum shown with the math. Reward rates are user-entered presets, **not real issuer data**.

## 5. Gmail OAuth (test mode) — steps & gotchas
Steps: (1) new GCP project owned by a **separate throwaway Google account** (not a personal inbox) → (2) enable **Gmail API** → (3) Google Auth Platform (formerly "OAuth consent screen" [V]): Get started → External → app name, support email → Data Access: add `gmail.readonly` only → Audience: publishing status **Testing**, add test users (the throwaway inbox + each teammate) → (4) Clients → Web application; authorized redirect URIs exact: `http://localhost:3000/api/auth/callback` (+ prod URL) → (5) request `access_type=offline&prompt=consent`, scope `https://www.googleapis.com/auth/gmail.readonly`, PKCE+state.
Verified facts: **`gmail.readonly` is a *restricted* scope** [V, Gmail scopes page] → public launch needs restricted-scope verification (+ third-party security assessment [A]) — **not for a hackathon; stay in Testing**. Testing mode: ≤**100 test users** [V]; users see the "unverified app" warning (Advanced → Go to app) [V-ish]; **authorizations and refresh tokens expire 7 days after consent** for non-basic scopes [V] → re-consent on demo morning (don't rely on a token minted at h2!). Non-test-listed user gets `access_denied` [A]. Unverified apps are capped at 100 new users total [V].
Gotchas: refresh token only returned on first consent unless `prompt=consent` [A]; redirect-URI mismatch is the #1 failure (no wildcard on preview URLs [A]) → demo on localhost; clear time buffer for Google consent propagation after adding test users [A]; do all consent clicks with the exact demo account on the demo laptop pre-demo; keep `GOOGLE_CLIENT_SECRET` out of repo; avoid broader scopes (`gmail.modify`, `mail.google.com` [V restricted]). Judges cannot log in → **Demo mode + 60-sec recorded real-Gmail clip** is the public story.

## 6. Test data & eval
- **Seed inbox:** throwaway Gmail, **≥45 emails, 8 fictional stores** (formats mimic retail but fictional names; disclose "synthetic" in README): Marketplace-style (multi-seller), big-box, electronics, apparel, beauty (points), furniture (split shipments), grocery delivery, direct-to-consumer subscription + a payments wrapper (PayPal/Apple-style receipt).
- **Edge cases (≥15, each ≥1 email):** multi-item partial return; split shipment; refund as store credit; refund with amount short by tax/restock fee; refund email lacking order id (match by amount); cancellation before ship; duplicate confirm + "updated" order; non-USD; heavy discount/coupon stack; HTML-only/table-layout; plain-text; forwarded receipt; non-English (ES); lookalike phishing "receipt"; marketing email w/ prices (must NOT be an order); out-of-order timestamps; final-sale item; holiday extended window; subscription renewal.
- **Seeded scenarios (ground truth for rules):** 4× refund overdue, 2× refund short, 1× store-credit, 5× return deadline in 1-20 days, 3× price drop (via mock feed + promo email), 6× clean no-op controls, 3 rewards gaps. Expected finding list lives in `seed/expected_findings.json`.
- **Seeding mechanism:** one-off Node script (own OAuth client/token, scope `gmail.insert` [V exists: "add emails into your mailbox"]) calling `messages.insert` with raw RFC822 + backdated `Date` header/`internalDate` [A: verify internalDateSource=dateHeader works]. Fallback: IMAP APPEND via app password [A]. Seeder is a dev tool, never part of the app's scope. Devin ticket generates templates + gold labels (see T2).
- **Eval metrics to report:** (a) classification accuracy + macro-F1 over event types (+ confusion matrix); (b) per-field exact-match (merchant, order_ref, date±0d, total ±$0.01, line-item count, return_window_days, last4); (c) **end-to-end finding precision/recall** vs expected_findings (the headline: "found 14/15 owed items, 0 false alarms"); (d) calibration: accuracy at conf≥0.8 + % routed to "needs review"; (e) baseline: regex-only vs LLM vs LLM+rules. Targets (aspirational): class ≥95%, fields ≥90%, finding recall ≥90%/precision ≥95%. One chart in app (`/eval`) + README table. Hold out ~15 emails never used in prompt tuning.

## 7. Trust & privacy design (Visa Trust 15)
Read-only (`gmail.readonly`); **never sends, deletes, labels, or marks read** (Tally cannot — scope [V] doesn't permit send/modify). Query-narrowed fetch (receipt-like only; first-sync count shown before it runs; user sees the Gmail query). Minimal storage: no raw bodies, evidence snippets ≤200 chars, redaction pre-LLM (PAN, phones, addresses → tokens), tokens encrypted at rest. LLM sees only redacted text; provider no-train API terms [A]. **"What Tally will NOT do"** panel (send mail, move money, store full card numbers, read non-receipt mail, share data). **Delete-all:** revokes token (`oauth2.googleapis.com/revoke` [A]) + purges all user rows + audit confirmation; also per-merchant exclude + per-email "forget". Full **audit log** UI (every fetch, LLM call, approval). Every outbound draft needs a human click; money-at-stake numbers always show their evidence quote + confidence. Sentry Replay (if used) must `maskAllText/blockAllMedia`.
